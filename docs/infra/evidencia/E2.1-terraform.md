# E2.1 — Infraestructura como código con Terraform

Este documento recoge la evidencia local del entregable **E2.1** y la HU-INFRA-06
relacionada. La ejecución contra el host on-prem queda registrada por el usuario en
`cg-tools` según el runbook.

## 1. Alcance declarado

Terraform declara la plataforma completa con módulos reutilizables, no solo el backend:

| Módulo | Recursos gestionados |
|---|---|
| `network` | Namespace, `ResourceQuota` y `NetworkPolicy` por ambiente |
| `compute` | Verificación del clúster k3d compartido `cg`, mirror de registro y puerto de Ingress `30080` |
| `registry` | PVC, Deployment `registry:2` y Service `registry:5000` |
| `storage` | Buckets MinIO con versioning y PVC de aplicación |
| `observability` | Helm `kube-prometheus-stack` y `loki-stack` con alertas |

Los ambientes parametrizados están en `infra/terraform/envs/{dev,stage,prod}` y usan
`backend "s3" {}` con claves `platform/<env>/terraform.tfstate` sobre MinIO `:9002` y
DynamoDB Local `:8000` (`hash_key = "LockID"`). El bootstrap es
`infra/terraform/state-backend/`.

## 2. Validación estática ejecutada

Comandos ejecutados sobre el repositorio (sin acceso al host on-prem):

```bash
terraform fmt -check -recursive infra/terraform
# fmt_exit=0
```

Copia aislada de `infra/terraform` (sin `.terraform`) y validación de cada raíz/módulo
con el plugin cacheado de `infra/terraform/envs/dev/.terraform/providers`:

```bash
terraform init -backend=false -input=false -plugin-dir=<providers>
terraform validate -no-color
```

## 4. Pipeline E2.3

`Jenkinsfile` incluye:

- Bootstrap en dos fases: `terraform apply -target=module.compute` antes del plan completo, para verificar el clúster compartido `cg` y que el contexto `k3d-cg` exista cuando se configure el provider.
- `Terraform Plan` para `dev`, `stage` y `prod`.
- `Trivy IaC` con `trivy config --exit-code 1 --severity CRITICAL` sobre Terraform y
  manifiestos Kubernetes (sin depender de la base de datos de vulnerabilidades del mirror on-prem).
- `Terraform Apply dev`, `Terraform Apply stage` y `Terraform Apply prod`; este último detrás de `Approval prod`.
- Imagen de Jenkins con Terraform 1.9.8 y Trivy 0.70.0.
- Credenciales `terraform-minio-creds` y `terraform-grafana-password`.

## 5. Ejecución en el host on-prem (205m07)

Ejecutada con autorización del usuario sobre el clúster k3d `cg` (contexto `k3d-cg`),
usuario `docker`. El backend remoto usa MinIO `:9002` + DynamoDB Local `:8000` y claves
`platform/<env>/terraform.tfstate`. Se aplicó primero
`terraform apply -target=module.compute` en cada ambiente y después el apply completo.

| Ambiente | Resultado del apply | Releases Helm | `plan -detailed-exitcode` |
|---|---|---|---|
| `dev` | Apply completado | `cg-dev-loki`, `cg-dev-prometheus` `deployed` | `0` (sin cambios) |
| `stage` | Apply completado tras corregir datasource y node-exporter | `cg-stage-loki`, `cg-stage-prometheus` `deployed` | `0` (sin cambios) |
| `prod` | `Apply complete! Resources: 13 added, 1 changed, 0 destroyed.` | `cg-prod-loki`, `cg-prod-prometheus` `deployed` | `0` (`No changes. Your infrastructure matches the configuration.`) |

Salida verificada en prod (`terraform plan -detailed-exitcode -no-color -input=false`):

```text
No changes. Your infrastructure matches the configuration.
Terraform has compared your real infrastructure against your configuration
and found no differences, so no changes are needed.
```

Estado final de los pods de prod: `cg-prod-prometheus-grafana` `3/3 Running`,
`prometheus-cg-prod-prometheus-kube-pr-prometheus-0` `2/2 Running`,
`alertmanager-cg-prod-prometheus-kube-pr-alertmanager-0` `2/2 Running`,
`cg-prod-registry` `Running`.

### Incidencias resueltas durante el apply

1. **Datasource duplicada (stage)**: `loki-stack` registraba Loki como `default`
   mientras `kube-prometheus-stack` registraba Prometheus como `default`, y Grafana
   abortaba con `Only one datasource per organization can be marked as default`.
   Corregido con `loki.isDefault=false`; en prod ambos datasources se verificaron
   antes de cerrar: Loki `isDefault: false`, Prometheus `isDefault: true`.
2. **node-exporter en clúster compartido (stage/prod)**: `hostPort 9100` ya estaba
   ocupado por dev y los pods quedaban `Pending`
   (`didn't have free ports for the requested pod ports`). Corregido con
   `node_exporter_enabled=false` en stage y prod.
3. **Grafana `pending-install` (prod)**: las migraciones SQLite tardaron ~19 min y la
   liveness probe por defecto (`delay=60s`, 10 fallos) reiniciaba el contenedor a mitad
   de la migración. Se ajustaron las sondas en vivo y se reflejó en IaC mediante
   `grafana_slow_start=true` (`initialDelaySeconds=600`, `failureThreshold=30`),
   dejando el release `deployed` y el pod `3/3`.

Tras reflejar el ajuste de sondas en IaC (`grafana_slow_start`) se ejecutaron los
applies finales: `APPLY_prod_RC=0` (`0 added, 1 changed, 0 destroyed`,
`cg-prod-prometheus` revisión 2 `deployed`) y `APPLY_dev_RC=0`
(`0 added, 2 changed, 0 destroyed`, `cg-dev-loki` y `cg-dev-prometheus` revisión 2
`deployed`). La verificación final de idempotencia arrojó
`PLAN_dev_RC=0`, `PLAN_stage_RC=0` y `PLAN_prod_RC=0`, con
`No changes. Your infrastructure matches the configuration.` en los tres ambientes.
Los datasources quedaron con un único `default` (Prometheus `isDefault: true`,
Loki `isDefault: false`) en prod y dev.

Los comandos y precauciones para reproducir estas verificaciones están en
[`docs/infra/runbook.md`](../runbook.md) §Terraform.
